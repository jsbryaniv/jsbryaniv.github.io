# Tutorial Authoring Guide

These instructions apply to everything under `_tutorials/`.

## Purpose

Create concise, practical programming tutorials for the website and for square social-media carousels. A tutorial should do more than document syntax: it should help readers decide when to use a feature, explain why it matters, and call out an important edge case or failure mode when one exists.

For current Python tone, pacing, and structure, use these as the primary references:

- `python/basic-is_vs_equals/tutorial.qmd`
- `python/basic-any_all/tutorial.qmd`
- `python/basic-dict_get/tutorial.qmd`

Prefer these recent examples over older tutorials when conventions differ.

## Files and Generated Artifacts

Each tutorial lives in a level-and-topic directory such as `python/basic-dict_get/`.

- `tutorial.qmd` is the source for the interactive tutorial and carousel content.
- `index.md` is the Jekyll page and contains website metadata.
- `tutorial.html` is generated by Quarto. Do not edit it by hand.
- `carousel/panel-*.png` and `carousel/carousel.pdf` are generated by `_tutorials/make_carousel.py`. Do not edit them by hand.

Do not render `tutorial.qmd` or regenerate `tutorial.html`, panel images, or the carousel PDF until the user has inspected the source draft and explicitly approved rendering. After approval, keep all generated artifacts in sync with the approved source.

## Directory and Metadata Conventions

Use a directory name with a difficulty prefix: `basic-`, `intermediate-`, or `advanced-`, followed by a short topic identifier consistent with the existing repository. Do not rename existing tutorial directories without an explicit request.

Start `tutorial.qmd` with:

```yaml
---
title: "Python Tip: `feature`"
subtitle: "A short statement of the practical benefit"
author: "Shep Bryan IV"
description: "A concise sentence describing what the reader will learn."
---
```

Create a matching `index.md` using the same title and description:

```yaml
---
layout: tutorial
title: "Python Tip: `feature`"
description: "A concise sentence describing what the reader will learn."
category: python_tips
tags:
  - python
  - basic
  - technical
# youtube_url: https://www.youtube.com/watch?v=YOUR_VIDEO_ID
---
```

Change the difficulty tag to match the directory. Preserve intentional metadata differences for non-Python tutorials.

## Editorial Style

- Write for programmers who know basic Python but may not know the featured tool or nuance.
- Use friendly, direct language and short sentences.
- Focus on one coherent lesson.
- Explain the reader's decision: when to use the feature, when not to, or how to choose between alternatives.
- Prefer concrete examples over abstract definitions.
- Build progressively from the basic behavior to realistic use, then nuance, an edge case, or a common mistake.
- Be opinionated when the guidance is well supported, while distinguishing language guarantees from implementation details.
- Avoid padding, exhaustive API tours, and jargon that is not needed for the lesson.
- Keep prose and code compact enough to fit comfortably inside a 500-by-500-pixel panel.
- Verify technical claims. Never rely on surprising behavior without checking it in the repository's Python environment.

## Panel Structure

Use one fenced div per panel and retain the numbered comments:

````markdown
<!-- PANEL 2 -->
:::{.tutorial-panel}

## Panel Heading

Short explanation.

:::{.code-animation}
```{python}
# Small, executable example
```
:::

:::
````

Use only as many panels as the lesson needs. Do not stretch a tutorial to reach a target count or retain a panel that does not add useful information. Give each panel one clear job.

### Opening panel

- Center it with `:::{.center}`.
- Use `# Python Tip: ...` as the heading.
- Open with a practical question, contrast, or reason to care.
- Summarize the core idea in two or three short lines.
- Include the empty `:::{.python-logo}` div.

### Teaching panels

- Use descriptive `##` headings.
- Put a short explanation before the example.
- Wrap executable examples in `:::{.code-animation}`.
- Keep examples independently understandable and outputs easy to interpret.
- Use comments only when they clarify intent, a contrast, or an expected failure.
- Add a short takeaway below the code when the implication is not obvious.
- Include a useful edge case or pitfall when it improves the reader's judgment; do not manufacture one merely to fill a panel.

### Wrap-up panel

- Center it with `:::{.center}`.
- Use `## Wrap-Up`.
- Restate the decision rule or main takeaway in memorable language.
- End with:

```markdown
Follow me for more tips.  
- Shep4
```

## Code Examples

- All Python cells must produce the behavior the prose claims. An intentional exception is acceptable when the error itself is part of the lesson, as in the `dict.get()` reference tutorial.
- `_tutorials/_quarto.yml` sets `execute.error: true`, so expected exceptions can appear in the rendered output without stopping the render. Treat every traceback as intentional only after verifying that it supports the lesson.
- Favor recognizable data and names such as users, scores, settings, and orders.
- Keep lines short and output limited so neither source nor output overflows a panel.
- Demonstrate behavior with `print()` when visible output strengthens the explanation.
- Do not add dependencies for a tutorial when the standard library can teach the concept cleanly.

## Render and Verification

Rendering is a separate, approval-gated phase. First create or revise the source files, give the user a concise summary, and wait for them to inspect the draft. Do not render the QMD or generate carousel artifacts in the same turn as the initial draft unless the user explicitly says to skip review or asks for immediate rendering.

After the user approves the source draft, continue with the workflow below.

From the repository root, render the tutorial with:

```bash
quarto render _tutorials/python/<tutorial-directory>/tutorial.qmd --to html
```

Rendering executes code through the `python3` Jupyter kernel. Because `_tutorials/_quarto.yml` sets `execute.error: true`, a cell error can be rendered rather than aborting the build. Inspect all outputs and tracebacks; do not mistake a completed render for proof that every example behaved correctly.

After a successful render, generate the carousel with:

```bash
_tutorials/.venv/bin/python _tutorials/make_carousel.py _tutorials/python/<tutorial-directory>/tutorial.html
```

Before considering the tutorial complete:

1. Confirm Quarto renders without an error.
2. Read the rendered output and confirm displayed results support the prose.
3. Generate every carousel panel and the PDF.
4. Visually inspect all panel images for clipped text, overflow, cramped code, awkward wrapping, and excessive empty space.
5. Confirm the opening and wrap-up panels are centered and the Python logo appears on the opening panel.
6. Confirm `tutorial.qmd`, `index.md`, `tutorial.html`, and the carousel artifacts agree on the topic and title.

## Scope and Preservation

When asked to create, draft, revise, complete, publish, or prepare a tutorial, change only the source files first. Stop after the draft and ask the user to inspect it. Rendering approval is not implied by words such as "create," "complete," "finish," "publish," or "prepare."

Only render the QMD and generate the carousel after the user explicitly approves the current source draft or directly instructs you to render it. If source content changes after approval, return it for inspection again before regenerating artifacts unless the user says another review is unnecessary.

Preserve unrelated work in the repository. Do not rewrite shared CSS, JavaScript, Quarto configuration, or the carousel generator merely to accommodate one crowded tutorial; simplify the panel content first.
